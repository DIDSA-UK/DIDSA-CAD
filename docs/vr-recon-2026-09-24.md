# VR/XR Companion Recon — 2026-09-24

Read-only research session. No code was changed. Scope: assess how much of the
existing FastAPI/OCCT backend a VR/XR companion (Quest 2/3 standalone + PCVR,
non-Flutter client) could reuse as-is, and where the Flutter client currently
carries logic that isn't backend-visible.

Investigated by reading `backend/app/document/*`, `backend/app/sketch/*`,
`client/lib/assembly/*`, `client/lib/viewport3d/*`, `client/lib/sketch/
local_solver/*`, `client/lib/storage/*`, and `docs/project-brief.md`/
`docs/assembly-scope.md`/`docs/lod-strategy/`.

---

## 1. Backend endpoints: reusable as-is?

Everything below is plain JSON-over-HTTPS (`X-API-Key` + `X-Document-Session`
headers), with zero Flutter/Dart coupling — any HTTP client (a Unity/OpenXR
app, a native engine, a C# or C++ client) can call these exactly as the
Flutter client does today. There is no WebSocket; it's synchronous
request/response, plus a narrow async job/poll mechanism for a few expensive
gear features (`POST .../bevel-pair-features/jobs`,
`GET .../jobs/{job_id}`).

**Import** (`backend/app/document/import_geometry.py`, `mesh_import.py`) —
`POST /parts/{id}/import-features`. Accepts STEP (round-trips through a temp
file into `STEPControl_Reader`, plus best-effort XCAF name/material read),
STL (binary or ASCII, auto-sniffed), OBJ, and **glTF** (`decode_gltf` in
`mesh_import.py` handles both binary `.glb` and JSON `.gltf`, magic-byte
sniffed — only the single-file-resolvable case, i.e. no external buffer URIs
split across files). All four decode into the same `MeshData`/`TopoDS_Shape`
pipeline every other feature uses. Fully reusable — format support is
already broader than the client UI currently exposes.

**Tessellation** — `GET /parts/{id}/mesh` (per-`Part` bodies) and
`GET /parts/{id}/assembly-mesh` (whole assembly scene, Phase 2 of
`docs/assembly-scope.md`). The latter is already shaped like a scene graph a
VR client would want: geometry is deduplicated by `part_id`
(`AssemblyBodyGeometry`, one mesh per unique Part) and a separate flat list
of `AssemblyOccurrenceInstance` entries each carry an `occurrence_path`, a
`world_transform` (already composed root-to-leaf via
`app.document.assembly.compose_chain`), `hidden`, and `color`. Both endpoints
return **JSON**, not a standard 3D format — vertices/normals/triangle indices
as flat float/int arrays (`MeshData`, `mesh_data.py`), unindexed
triangle-soup (3 fresh vertices per triangle, no vertex welding). A quality
slider (`quality=0..1`, mapped to OCCT deflection tolerances,
`mesh_quality_from_slider`) and a coarse LOD tier (`tier=coarse`, real cheap
OCCT primitives standing in for a handful of expensive feature types — gears,
lofts, patterns) already exist and were tuned for a Raspberry Pi 5 target,
which happens to line up well with a standalone Quest's frame budget.

**Export** — `GET /parts/{id}/export/{step,stl,obj,glb}` and the assembly-
scoped siblings `export/assembly-{step,stl,obj,glb}` (walks the occurrence
tree, applies each instance's real world transform, and — for STL/OBJ/glb —
flattens everything into **one merged mesh**; for STEP, each instance's shape
stays a separate solid in the output compound). `glb` export already exists
and is real binary glTF 2.0 (`app/document/mesh_export.py::encode_glb`) —
but it's a single mesh/single node/no-material, POSITION+NORMAL-only,
unindexed snapshot; not a scene graph and not something built for repeated
polling.

**Solver** — two independent solvers, both real geometry/constraint solving,
no stub logic:
- 2D sketch solver: `app/sketch/solver.py`, wraps `py_slvs.slvs.System`
  (`py-slvs`, a `realthunder/solvespace` binding). `POST /sketches/{id}/
  solve(-and-refresh)`.
- Assembly mate solver: `app/document/assembly_solver.py`, same underlying
  library used in free-3D mode (`addTransform`/`addSameOrientation`/
  `addPointPlaneDistance`/etc., `wrkpln` omitted). `POST /parts/{id}/
  occurrences/{id}/solve`, plus Mate CRUD at `/parts/{id}/mates`. v1 scope
  limit: solves one *driven* Occurrence against fixed peers only — no
  simultaneous multi-body solve, and only top-level Occurrences (a Mate can't
  reference an Occurrence nested inside another Occurrence yet).

**Bottom line**: every one of import/tessellate/export/solve is engine- and
UI-framework-agnostic already. A VR client talks to the exact same endpoints
the Flutter client does. The gaps are about *shape of the data* (JSON
triangle-soup, not glTF; flattened export, not a live per-part/instance
scene), not about the backend being tied to Flutter in any way.

## 2. Could the backend return glTF meshes per part/assembly?

Yes, and most of the hard part is already built. `GET /parts/{id}/
assembly-mesh` already computes exactly the data a per-part/per-instance
glTF scene needs — deduplicated per-part geometry + a flat instance list with
resolved world transforms — it's just currently serialized as this app's own
JSON shape (`BodyMeshResponse`/`AssemblyOccurrenceInstance`), not as glTF
nodes.

To get there:

1. **New encoder**, alongside `mesh_export.py::encode_glb`, that emits one
   glTF `mesh` per unique `part_id` (reusing `_assembly_body_mesh_responses`'
   per-part `MeshData`) and one glTF `node` per `AssemblyOccurrenceInstance`,
   with `node.mesh` pointing at its part's shared mesh — i.e. glTF's own
   native node/mesh instancing, which is exactly what the current dedup-by-
   part-id design already computed server-side.
2. **Transform conversion**: `AssemblyOccurrenceInstance.world_transform` is
   axis-angle (`RigidTransform`, translation + rotation_axis +
   rotation_angle_degrees) — needs converting to a glTF node's
   `translation`/`rotation` (quaternion) or a 4x4 `matrix`.
   `assembly_solver.py` already carries axis-angle↔quaternion conversion at
   its own `py_slvs` FFI boundary (that module's own docstring flags this as
   the *only* place a quaternion appears in the backend today) — that
   conversion is directly reusable, not new math.
3. **Materials/color**: today `encode_glb` only emits POSITION+NORMAL, no
   material. `AssemblyOccurrenceInstance.color` (hex string, per-Occurrence)
   would need to become a glTF `material.pbrMetallicRoughness.baseColorFactor`
   — either one material per distinct color (cheap, few colors in practice)
   or per-vertex color as a fallback.
4. **Hidden flag**: either omit hidden instances from the glTF node list
   server-side, or emit them and let the client filter — the JSON endpoint
   currently does the latter (reports `hidden`, client hides in the
   viewport); worth picking deliberately since VR clients may want the
   server to do the filtering to save payload.
5. **Indexing** is optional for validity but worth adding: current
   `MeshData` is deliberately unwelded triangle-soup (see `mesh_data.py`'s
   own comment on why — avoids a merge/reindex step, matches the client's
   own flat-buffer rendering convention) — fine for a snapshot export, but
   an indexed accessor would meaningfully cut payload size for a scene with
   many repeated/patterned components (which is exactly where glTF node-
   instancing helps most).
6. **LOD**: the existing `tier=coarse` mechanism could feed a fast low-
   triangle glTF for the handful of feature types it already covers
   (gear/bevel/loft/pattern families), letting a VR client paint something
   immediately while full detail is fetched — same pattern already used for
   the flutter viewport's coarse-preview UX (`docs/lod-strategy/`).

None of this requires new geometry/tessellation work — `compute_part_bodies`
and `tessellate_shape` stay exactly as they are; it's an additive encoder +
either a new endpoint (`GET /parts/{id}/assembly-mesh.glb` or similar) or a
`format=` query param on the existing one. Estimated effort: comparable to
`mesh_export.py` itself (a few hundred lines, well-precedented pattern in
this codebase — `encode_stl`/`encode_obj`/`encode_glb` are each under ~40
lines). The one real design decision to make up front is whether per-part
glTF meshes get served as separate small files (many round trips, better for
partial/incremental loading — closer to how you'd want to stream a big
assembly into a headset) or as one glTF scene per call (fewer round trips,
simpler, closer to what exists today) — worth deciding against the actual
VR frame/load-time budget before building it.

## 3. Native file format: documented? independent of Flutter?

**Documented, informally**: `backend/app/document/native_format.py`'s own
module docstring plus per-dataclass docstrings in `models.py` are the closest
thing to a spec — there is no separate JSON-schema file or dedicated format
doc. `docs/assembly-scope.md` §2 ("The data model") is the best narrative
walkthrough of the `Part`/`Occurrence`/`Mate` shape. `SCHEMA_VERSION = 1`
(`native_format.py:162`) is checked for an **exact match** on import
(`import_native` raises `NativeFormatError` on any mismatch, no forward/
backward compat logic beyond that single integer today) — see
`backend/tests/test_didsacad_backward_compat.py` for the current compat
test matrix.

**Independent of the Flutter client, mostly, with one real exception**:

- **A single `.didsa` file's own JSON** (`export_native`/`import_native`,
  `GET /export/native` / `POST /import/native`) is a "pure parametric tree"
  — every `Part`'s ordered `Feature` list plus every referenced `Sketch` —
  deliberately kept as "a standalone dict<->dataclass mapping, not a reuse of
  `app.document.schemas`'s pydantic response models" (that module's own
  docstring). The backend owns this format completely; the client's only job
  is writing the returned dict to disk and reading it back. Genuinely
  client-agnostic.

- **Multi-file assembly composition is not.** `Occurrence.external_ref` (a
  string naming another `.didsa` file) is, by deliberate design (
  `docs/assembly-scope.md` §1 decision #6), **opaque to the backend** — "it
  has no filesystem/SAF access at all... stores and echoes back verbatim and
  never parses or resolves" it. Resolving a root file's referenced graph,
  detecting reference cycles, falling back to a cached snapshot when a
  referenced file is unreachable (decision #5), and composing everything
  into the one combined payload `POST /import/native` expects is **entirely
  implemented in Dart** — `client/lib/assembly/assembly_graph_composer.dart`
  — on top of a Flutter-specific storage abstraction (`client/lib/storage/*`:
  Android SAF, an iOS bookmark platform channel, plain desktop paths,
  `FileCache` for the stale-snapshot fallback). A non-Flutter client gets the
  single-file JSON format for free, but the "assembly of files" *protocol* —
  how a project's `.didsa` files reference each other and how one caller
  assembles them into one session — has no server-side or format-level
  definition beyond "some opaque string, resolved by convention client-side."
  Worth treating as a real open design question for a headset client, not
  just a porting task — a standalone Quest has no equivalent of Android SAF
  or a desktop filesystem, so this layer likely needs rethinking (sync from
  a paired phone/PC, a lightweight companion service, cloud storage) rather
  than reimplementing SAF-shaped semantics.

## 4. Dart-client logic that would need to move server-side or be reimplemented

1. **Local (client-side) 2D sketch solver** —
   `client/lib/sketch/local_solver/local_sketch_solver.dart` is an explicit,
   line-by-line Dart port of `backend/app/sketch/solver.py`
   (`_solve_sketch_once`, every `Constraint.add_to_solver`), built on
   `dart:ffi` bindings (`slvs_bindings.dart`) to the same native SolveSpace
   library the backend calls via `py_slvs`. It exists purely so dragging a
   sketch point solves locally, without a network round trip per frame. This
   is real duplicated business logic (redundancy-safe-type convergence
   overrides, provisional-DOF floors, anchor-pinning semantics — all called
   out in its own doc comment as deliberate, verbatim ports, not
   simplifications), and it is Dart/FFI-specific in its current binding
   layer (the underlying `.so`/native lib is portable C, the glue code
   calling it is not). A VR client has the same responsiveness problem in an
   arguably worse form — dragging geometry in 3D over a network round trip
   per frame is a worse experience than 2D sketch dragging — so this is a
   real question to resolve early: reimplement an equivalent local solve
   against the same native library from the new client's own language/
   engine, or accept round-trip latency and design the interaction around it
   (e.g. solve-on-release rather than solve-while-dragging).

2. **Assembly graph composition + storage abstraction** — see Q3 above
   (`assembly_graph_composer.dart`, `client/lib/storage/*`,
   `save_all.dart`'s `external_ref` stamping on Save All). Entirely Dart,
   entirely tied to Flutter's platform-channel storage plugins. Needs a
   genuinely new implementation for a headset client, not a straight port —
   the storage model itself likely needs to change (see above).

3. **Mate/selection authoring** — the mate *solve* is backend logic and
   fully reusable (item 1 above), but *picking* the two entities that become
   a `MateEntityRef` depends on client-side 3D hit-testing
   (`client/lib/viewport3d/selection_hit_test.dart`,
   `selection_filter.dart`) coupled to the Flutter-rendered mesh
   (`mesh_geometry.dart`). The underlying data those hit-tests run against —
   `face_ids`/`edge_ids`/`topology_vertex_ids` on `BodyMeshResponse`, per
   the "Stage 23" fields in `mesh_data.py` — is already engine-agnostic
   (dense, stable-per-request ids parallel to the tessellation arrays), so a
   VR client can reimplement raycasting/picking against its own renderer
   using the same ids without needing new backend support; it just can't
   reuse the Dart hit-testing code itself.

4. **Rendering** — `flutter_scene` (`client/lib/viewport3d/part_viewport.dart`,
   `mesh_geometry.dart`) is Flutter/Impeller-specific and not reusable at
   all. A VR client needs its own renderer (Unity/Unreal/native OpenXR +
   scene graph) consuming either the existing JSON mesh endpoints or a new
   glTF endpoint (Q2).

5. **Feature tree / assembly tree UI** — good news here:
   `feature_tree_panel.dart`'s `featureDisplayName` and similar are thin
   display-label mappings over a backend-provided `FeatureDto` list; the
   real dependency-graph/recompute logic lives entirely server-side
   (`app/document/graph.py`). Minimal reimplementation burden — a VR client
   just needs its own tree/list UI reading the same `GET /parts/{id}/
   features` endpoint.

6. **Focus-stack / assembly-lens state**
   (`client/lib/assembly/focus_stack.dart`) — pure client-side UI state
   (which Part is currently "focused" for in-context editing), never
   persisted server-side. Trivial to reimplement as ordinary app state in
   any client.

7. **AI-assisted design** (`client/lib/ai/*`) — per README, the AI plan
   pipeline talks to the same Sketch/Feature API a human uses, so it's
   portable in principle, but the prompt/orchestration logic
   (`ai_plan_translator.dart` etc.) lives in Dart today. Likely out of scope
   for a first VR companion pass; flagging only for completeness.

## 5. Stateless-backend design: blockers for multi-user shared assemblies

Multi-user/concurrent editing was **explicitly out of scope from the
original design** (`docs/project-brief.md` §9 lists both "Multi-user/
concurrent editing" and "Server-side persistence or accounts" as
deliberately deferred). Concretely, what would need to change:

- **"Session" means "one device", not "one user" or "one document".**
  `app/session_context.py` binds a session id from the client-set
  `X-Document-Session` header; `app/document/store.py` keeps one in-memory
  `Document` per session id (`OrderedDict`, LRU-evicted at 200 entries).
  There is no separate concept of "which document is open" vs. "who is
  connected" — two headset users wanting to look at *the same* assembly
  would either (a) each get their own isolated in-memory copy under
  different session ids, with no way to see each other's edits at all, or
  (b) have to deliberately share one session id, in which case there is
  **no concurrency control whatsoever** — `store.py`'s lock only protects
  the dict lookup, not a document mutation sequence, so two clients editing
  under the same session id would race and silently clobber each other's
  changes (last write wins, no merge, no conflict signal).

- **No persistence beyond client-held files.** The in-memory `Document` is
  the only copy of anything not yet exported; a backend restart, redeploy,
  or LRU eviction loses it outright. There is no server-side source of truth
  a second viewer could sync against even in principle — "shared assembly"
  today can only mean "share the `.didsa` files," never "share a live
  session."

- **No real-time push channel.** REST only, no WebSocket/SSE. A second
  viewer wanting to see a collaborator move a part has to poll
  `GET /assembly-mesh` repeatedly — workable for occasional catch-up, not
  for the near-real-time feel a shared VR review session would want.

- **No per-user identity or authorization.** Auth is one shared static
  `X-API-Key` (`app/auth.py`'s own docstring: "not a multi-user auth
  system... no rate limiting, per-client revocation, rotation"). Every
  connected client is anonymous and equally privileged — there's no
  identity the mate solver, occurrence store, or a future locking/presence
  system could hang "who's currently dragging this part" off of.

- **Filesystem/project ownership is entirely client-side**
  (`docs/assembly-scope.md` decision #6: "the backend stays stateless — it
  has no filesystem/SAF access at all"). There's no server-side notion of
  "a shared project" to attach multi-user access control, locking, or
  presence to — that concept doesn't exist on the backend today in any form.

**Net**: none of this is a small config change — genuine multi-user shared
assemblies would need new backend infrastructure on at least four axes:
(1) separating "session" (who's connected) from "document" (what's open, one
document reachable by many sessions), (2) real persistence so a document
outlives any one connection, (3) a concurrency/merge or locking model for
Occurrence transforms and Mates (the mate solver's own "v1 only drives the
actively-dragged Occurrence against fixed peers" scope limit already hints
at where multi-writer conflicts would first surface), and (4) a push channel
for low-latency updates. This is a substantial follow-on project, not a
VR-client-side workaround — worth scoping separately before committing to
"shared assembly review" as a VR feature, versus starting with single-user
VR viewing/editing of a locally-held assembly (which everything in §1-4
above already supports).

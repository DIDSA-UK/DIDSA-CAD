## 1. `assembly_graph_composer.dart`'s `external_ref` resolution — portable to Python?

Read in full (`client/lib/assembly/assembly_graph_composer.dart`,
`client/lib/storage/file_cache.dart`, `client/lib/assembly/relative_path.dart`).

**Paths are always relative, never absolute.** `Occurrence.external_ref` is
validated at authoring time (`relative_path.dart::validateProjectRelativePath`)
to reject a leading `/` or `\`, a Windows drive letter (`^[a-zA-Z]:`), and any
`..` segment — so by construction every `external_ref` a client ever writes is
a plain forward-slash-or-backslash path relative to the open project's own
root (`ProjectRoot`), never an absolute path or a path that can climb outside
the project. The composer itself does no further validation at resolve time —
it trusts every `external_ref` it reads back out of an already-saved file,
because only this same validated-write path could have produced it.

**Cycle detection** is a plain DFS with an explicit ancestor-path list, not a
global visited-set:
```
resolvePart(path, ancestorPath):
    if path in ancestorPath: raise CycleException(ancestorPath + [path])
    if path already resolved: return its cached Part id      # diamond, not a cycle
    payload = readAndDecode(path)                             # live, or cached-stale fallback
    for each Occurrence in payload's single Part:
        if Occurrence.external_ref: resolvePart(external_ref, ancestorPath + [path])
    cache and return this Part's id
```
The ancestor-path check (not a "seen anywhere" set) is what correctly
distinguishes a genuine cycle (A→B→A) from the expected, supported diamond
case (A→B, A→C, B→D, C→D — D resolved once, reused twice) — a Part already
fully resolved via one branch is served from `partIdByPath`'s cache when a
second branch reaches it, no re-read, no false-positive cycle.

**Stale-snapshot fallback** (`docs/assembly-scope.md` decision #5): every
read tries the live file first; on `StorageException` it falls back to
`FileCache` (a local, content-addressed-by-`(root, relativePath)` cache of
the last successfully-read bytes plus their last-known-modified time) and
flags that path in `staleRelativePaths`. A **root** file that can't be read
live *or* from cache is fatal (`compose()` throws); a **referenced child**
that can't be read either way is not fatal — `resolvePart` returns `null`,
the Occurrence pointing at it is simply left with no `resolved_part_id`, and
every other sibling still resolves. This mirrors the backend's own
`get_assembly_mesh` walk, which silently skips an unresolved Occurrence
rather than failing the whole response.

**Could it be ported to Python as-is?** Yes, essentially line-for-line, and
it would actually get *simpler* moving server-side, not harder:

- The algorithm itself (DFS + ancestor-path cycle check + path-keyed memo
  dict + JSON dict manipulation) has zero Dart-specific behavior — it's
  ordinary recursive graph traversal over `dict`/`list` structures, directly
  expressible in Python with the same shape (an `async def resolve_part(path,
  ancestor_path)` or a plain sync version, a `dict[str, dict]` memo, a
  `list[str]` ancestor stack).
- The one real dependency, `StorageService` (`_storageService.resolve` /
  `.readFile` / `.lastModified`), is the part that's genuinely
  Flutter-specific today (Android SAF, an iOS bookmark platform channel,
  `dart:io` for desktop) — but a **server-side** composer doesn't need any of
  that. A backend process reading from a real, server-mounted filesystem (a
  network share, a bind-mounted volume) just needs `pathlib`/`open()` against
  a configured project root — no SAF-equivalent, no platform channel, no
  persisted-URI-permission dance. That whole abstraction layer disappears
  rather than needing a port.
- The stale-snapshot cache (`FileCache`) is the one piece worth rethinking
  rather than copying verbatim: it exists specifically to cope with a mobile
  client's storage going briefly unreachable (SAF permission revoked, offline
  SD card). A server sitting in front of its own mounted network share has a
  different failure mode (the share itself going unreachable, not a
  permission grant) — worth keeping the same "stale flag, don't hard-fail a
  child" policy, but the caching layer underneath it would more naturally be
  a local disk cache directory or an in-memory LRU than a port of
  `FileCache`'s own SHA256-keyed-file-pair scheme.
- `native_format.py`'s existing `NativeFormatError`/`SCHEMA_VERSION` checks
  and the "trust `resolved_part_id` only when it names a Part in this same
  payload" validation (`import_native`, per `Occurrence`'s own docstring)
  already do, server-side, exactly the payload-shape checking the composer's
  `if parts.length != 1: throw FormatException(...)` does client-side today —
  so a server-side composer gets that validation for free from code that
  already exists, rather than needing to duplicate it.

**Net**: this is a good, low-risk candidate for a straight port — the
algorithm is simple, well-isolated, and already has no OCCT/geometry
dependency (pure path/JSON logic, `app.document.native_format`-adjacent, not
`app.document.extrude`-adjacent). The honest new work is designing the
server's own storage/mount model (see Q2/Q5) and the caching policy above,
not the traversal algorithm itself.

## 2. File granularity: what's in the assembly file vs. each part's file?

From `Part`'s own docstring (`backend/app/document/models.py:2867`) and
`Occurrence`'s (`:3115`): **there is no separate "assembly file" type.**
Every `.didsa`/`.DIDSAprt` file is exactly one `Part`, and a `Part` always
carries three independent pieces of data at once:

| Data | Lives in |
|---|---|
| `features` (this Part's own local Feature/solid-modeling history) | **this file only** |
| `occurrences` (which other Parts are placed as components *of this Part*, and where — `transform`/`hidden`/`fixed`/`color`/`suppressed`, plus `external_ref`, the opaque relative-path pointer to each referenced file) | **this file only** |
| `mates` (constraints between *this Part's own* Occurrences) | **this file only** |

Critically: **a referenced child Part's own file has no idea it's referenced.**
Placement data (an Occurrence's `transform`) and constraint data (a Mate)
live entirely on the *referencing* (parent) Part, never on the referenced
(child) Part — the child file, opened alone, is just its own local feature
history, exactly as if it had never been placed into any assembly at all.
This is stated directly in `Part`'s docstring: "Parts never reference each
other or share Features/Sketches/Points" (decision #3) — an Occurrence is a
one-directional, parent-owned pointer, not a bidirectional link.

**Two users, two files → no collision.** If User A opens `Bracket.DIDSAprt`
directly and adds a fillet (edits `features`), and User B has
`TopAssembly.DIDSAprt` open and drags `Bracket`'s Occurrence to a new
position (edits `occurrences` on a *different* file), each `savePart` call
(`assembly_document_client.dart::savePart` → `exportNative(partId:...)` →
`writeFile`) writes only its own Part's file. No shared byte range, no
overwrite — this is a genuine strength of the "assembly structure lives on
the referencing Part, not the referenced one" model.

**Two users, the *same* file → last write wins, whole-file.** Every save is
a **full-file overwrite** — `export_native(part_id=X)` serializes that one
Part's *entire* current state (every Feature, every Occurrence, every Mate,
all Part-Properties fields) and `writeFile` replaces the file's full
contents; there is no partial/field-level write anywhere in this path. So if
two users are both looking at `TopAssembly.DIDSAprt` — say User A adds a
Mate while User B, at the same moment, drags an unrelated Occurrence to a
new position — both edits live in the same file's `occurrences`/`mates`
lists, both users' sessions hold their own independent in-memory copy of the
whole Part (per-session `Document`, `app/document/store.py`), and whichever
`savePart` call lands second **silently discards every change the other user
made to that file**, not just the conflicting field — there is no merge, no
diff, no conflict error. This includes "Save All"
(`assembly_document_client.dart::saveAll`), which re-imports and re-stamps
every Part in `relativePathByPartId` from one session's own full-session
export before writing each file — a second concurrent "Save All" from
another session would do the same, each blind to the other's in-flight
changes.

**Practical implication for a shared-storage design**: the natural
concurrency-safety unit this data model already gives you for free is
*one Part = one file*, matching a real filesystem's own natural unit (one
file, one writer at a time is a solvable problem; one field inside one file,
shared by many writers, is a much harder one). A shared-storage server
sitting between clients and a network share could get meaningful safety
cheaply by adding **per-file optimistic concurrency** (an ETag/version/hash
check on write — reject or merge-prompt a save whose base version doesn't
match the file's current version) at the file-write boundary, without
needing to touch the in-memory Document model at all. What it would *not*
solve on its own: two users both actively editing the **same** assembly file
concurrently (not just saving at different times) still need either explicit
locking ("only one editor of `TopAssembly.DIDSAprt` at a time") or a real
merge story for `occurrences`/`mates` — the file-per-Part boundary limits the
blast radius of a collision, it doesn't eliminate collisions on a file two
people are actively both editing.

## 3. Size and speed: `GET assembly-mesh` payload, real measurement

No real example `.didsa` project files exist in this repo to measure
directly (it's a from-scratch hobby project; the largest assembly-shaped
test fixture in `backend/tests/` uses only 2 Occurrences). To get real
rather than purely theoretical numbers, this session started a temporary
local backend instance (`uvicorn`, default settings, in-memory only — no
repo files touched) and built a genuinely representative "large assembly"
through the real API: a base `Bracket` Part (384-triangle imported mesh)
plus `Bolt`/`Washer` Parts (96-triangle imported meshes each), placed as a
10×8 linear grid (bolt+washer pairs) and a 24-around circular pattern of
bolts — a real bolted-flange-shaped assembly, built the same way
`ComponentPattern` lets a real user build one cheaply.

**Result: 4 unique Part geometries, 186 placed Occurrence instances.**

| Call | Size | Time (server-local, no network) |
|---|---|---|
| `GET /parts/{id}/assembly-mesh` (JSON, default quality) | **470,450 bytes (~460 KB)** | **~45 ms** (5 runs: 42.7–49.7 ms) |
| `GET /parts/{id}/assembly-mesh?quality=1.0` (finest) | 470,450 bytes (identical) | ~44 ms |
| `GET /parts/{id}/export/assembly-glb` (existing flattened export) | **1,327,692 bytes (~1.3 MB)** | 573 ms |
| `GET /parts/{id}/export/assembly-stl` | 921,684 bytes | 612 ms |
| `GET /parts/{id}/export/assembly-step` | 219,921 bytes | 41 ms |

(Caveat: because the test geometry was built via STL import rather than
parametric features/fillets, `quality` has no effect on it — an imported
mesh's triangulation is fixed at import time, unlike an Extrude/Revolve/
Fillet's analytic OCCT surface, which *does* re-tessellate at a finer/coarser
deflection. The size/time numbers above are representative of payload scale
for a real assembly at this instance count; they don't demonstrate the
quality slider's effect, which would need a fixture built from real
parametric features instead.)

**Where the 460 KB actually goes** (inspected directly): the JSON response
splits roughly 98%/12% between the `geometry` section (unique per-part mesh
data, deduplicated) and the `instances` section (one small entry per placed
Occurrence — id/path/transform/color/hidden, ~294 bytes each × 186 ≈ 54.6
KB) — confirming the backend's per-Part-id dedup (`_geometry_for`,
`get_assembly_mesh`'s own docstring) works as designed: **the payload does
not scale with instance count for the expensive part** — 186 instances of 4
unique geometries cost roughly what 4 geometries + 186 small transforms
costs, not what 186 full geometries would cost.

Within one body's own mesh data, though, more than half the bytes are
**not** what a renderer needs at all: for one 96-triangle body,
`vertices`+`normals` (what any renderer needs) totalled ~20 KB, while
`edges` (the flat polyline-segment array used only for the viewport's own
wireframe/edge-highlight rendering, `mesh_data.py`'s Stage 11 field) alone
was ~19.8 KB — roughly as much as the actual visual geometry — with
`face_ids`/`edge_ids` (hit-testing ids, Stage 23) adding a further ~1.4 KB.
`GET /assembly-mesh` is genuinely a **CAD-viewport payload** (rendering +
wireframe + face/edge/vertex hit-testing all in one response), not a
render-only one — a VR client that only needs to *draw* the scene is paying
for roughly 2x more JSON than its actual rendering needs, before even
accounting for JSON's own text-encoding overhead against a binary format.

**glTF estimate, now grounded in a real measurement.** The existing (already
implem0ented) `export/assembly-glb` endpoint gave a real, empirical
number for the *flattened, non-instanced* case: 1.33 MB, because it
re-emits full triangle data for **every one of the 186 instances**
separately (confirmed via the file's own glTF accessor: 55,296 vertices =
18,432 triangles — 186 instances × ~99 triangles/instance average, vs. only
**960 unique triangles** across the 4 real Part geometries). A per-part
**node-instanced** glTF (Q2 of the prior recon report) — one mesh per unique
Part, one lightweight node per instance, reusing `mesh_export.py`'s existing
POSITION+NORMAL-only unwelded encoding — would need only:
- BIN chunk: `2,880 unique vertices × 2 (position+normal) × 3 floats × 4
  bytes ≈ 69 KB`
- JSON chunk: ~186 small node entries (translation + rotation quaternion) at
  roughly 100–150 bytes of JSON text each ≈ 20–28 KB, plus a few KB of
  fixed mesh/accessor/material boilerplate for 4 meshes

**≈ 90–100 KB total** — about **5x smaller than the current JSON
`assembly-mesh` response** (470 KB) and about **13–15x smaller than the
existing flattened `.glb` export** (1.33 MB), for the *identical* real
assembly. This is a large, concrete number in favor of building the
per-part/instanced glTF encoder discussed in the prior recon report,
specifically for a bandwidth/frame-budget-constrained standalone headset.

## 4. Plain HTTP over LAN: Android/Quest client, TLS requirement, API key handling

**The backend itself never terminates TLS.** `backend/Dockerfile`'s own
`CMD` launches `uvicorn app.main:app --host 0.0.0.0 --port 8000` with no
`--ssl-certfile`/`--ssl-keyfile` anywhere in this codebase — confirmed by
searching the whole repo. Every current real deployment gets HTTPS, if it
gets it at all, from something *in front of* uvicorn: the documented
production path is Cloudflare Tunnel (`docs/project-brief.md`'s hosting
section) terminating TLS at Cloudflare's edge before proxying plain HTTP
into the container. The Termux/on-device deployment (README: "the backend
runs directly under Termux/proot Debian on-device") talks to the Flutter app
over `http://127.0.0.1:8000` — **plain HTTP, no TLS at all** — because
client and server share one device. **Plain HTTP LAN access to the backend
is therefore not a new capability to build — the backend already only ever
speaks plain HTTP; TLS, when present, is bolted on externally, never by
uvicorn itself.**

**The client has no scheme requirement either.** `ApiConfig.baseUrl`
(`client/lib/config.dart`) is stored and used as an arbitrary string (doc
comment's own example: `https://cad-api.snail-shell.uk`, but nothing
enforces the scheme); `ConnectionScreen`'s health check just does
`http.get(Uri.parse('$url/health'), ...)` — `http://192.168.1.50:8000` works
exactly the same way as an `https://` URL as far as this client code is
concerned.

**The real blocker is Android's own platform default, not this app's
backend or client code.** `client/android/app/src/main/res/xml/
network_security_config.xml`, referenced from `AndroidManifest.xml`'s
`android:networkSecurityConfig`, explicitly scopes plain-HTTP permission to
loopback only:

```xml
<domain-config cleartextTrafficPermitted="true">
    <domain includeSubdomains="false">127.0.0.1</domain>
    <domain includeSubdomains="false">localhost</domain>
</domain-config>
<base-config cleartextTrafficPermitted="false" />
```

— with a comment explaining exactly why: Android blocks cleartext traffic
by default for a modern `targetSdkVersion`, so this carve-out exists purely
to let the on-device Termux backend (`http://127.0.0.1:8000`) work at all;
**every other host, including a LAN IP, is still blocked by the `base-config`
default today.** This means: as currently configured, if a Quest build were
produced from *this same Flutter codebase* unmodified, pointing it at a LAN
server's IP over plain HTTP would be silently rejected by Android's network
stack before the request ever leaves the device — not a backend limitation,
a client manifest setting. Fixing it (for either a Flutter-built Quest app or
a new non-Flutter native Quest app, which would need to make this same
choice independently in its own manifest) means either:
- adding a scoped cleartext exception for the LAN server's own address/CIDR
  range (mirroring the existing loopback carve-out, just widened deliberately
  and narrowly), or
- requiring TLS even for the LAN case (self-signed cert, which then needs
  either a custom trust anchor bundled with the app or a real cert from a
  local CA/mkcert-style tool — meaningfully more setup for a "just works on
  my home WiFi" experience than the loopback case already has).

**API key handling** is unaffected either way — it's a single static secret
sent as `X-API-Key` on every request (`app/auth.py`) regardless of transport,
with the same caveat this and the prior report both flag: over plain HTTP,
that header (and the whole model payload) is visible to anything else on the
same LAN segment — acceptable for a private home network in the same threat
model the Termux/loopback case already accepts, but worth stating
explicitly rather than assuming "LAN" implies "private."

**Bottom line**: plain HTTP on a LAN is technically fully supported by the
backend today (it never does anything else) and by the existing client code
(no scheme validation) — the one concrete piece of new work is a scoped
Android network-security-config exception (a few lines of XML, same shape as
the existing loopback one) for whichever app (Flutter-rebuilt or a new
native one) runs on the Quest, plus a considered decision on how far to widen
that exception (a specific server IP vs. a private-IP-range default).

## 5. Which roadmap item would hold server-side composition + shared storage?

**None today.** Searched `docs/roadmap.md`, `docs/assembly-scope.md`,
`docs/didsa-longterm-vision-and-model.md`, and `README.md` for any existing
"shared storage," "network storage," "multi-user," or "server-side
composition" item — the only two hits are both explicit statements of the
**opposite** of this design, both framed as "locked in" decisions:

- `docs/assembly-scope.md` §1 **decision #4**: "Storage: user-chosen project
  folder via Android/iOS Storage Access Framework... or a plain path on
  desktop... Network storage = whatever the OS/SAF already exposes as a
  folder — **no built-in SMB/WebDAV client.**"
- `docs/assembly-scope.md` §1 **decision #6**: "The backend stays
  stateless — it has no filesystem/SAF access at all... The client resolves
  every referenced file itself."

Both are listed under "Model decisions (locked in, drive every phase
below)" — i.e. every one of Phases 0–9 in that document was built assuming
these hold. Moving composition server-side and adding real shared network
storage doesn't extend this document's scope, it **reopens two of its
foundational decisions** — worth stating plainly rather than trying to slot
this in as an incremental addition to an existing phase list.

`README.md`'s "Future ideas" section already lists "VR design review and
manipulation" as a one-line bullet with no linked scoping doc — the closest
existing anchor point, but it's aspirational/unscoped, not a tracked
roadmap item with phases the way Assemblies or Gear Design have.

**Where this should go**: this needs its own scoping document, written the
same way `docs/assembly-scope.md` and `docs/pattern-mirror-scope.md` were —
a "Model decisions (locked in)" section that explicitly supersedes decisions
#4 and #6 above (not silently contradicts them), followed by a phased plan.
Reasonable candidate name: `docs/shared-assembly-storage-scope.md` (or
folded into a renamed/expanded VR scoping doc if the VR client and shared
storage are being designed together, since — per §1 of this report and §4-5
of the prior one — the server-side composition work is a prerequisite for a
storage-constrained headset client regardless of the multi-user question).
Until such a doc exists, `docs/roadmap.md`'s "Other open items" section
would be the right place for at least a placeholder entry, so this doesn't
get lost between the two recon reports and an eventual scoping pass.

## Appendix: how the measurement assembly was built (for reproducibility)

Not committed to the repo (in-memory backend state only, discarded when the
test server stopped). For a future session wanting to reproduce or extend
this: `POST /document/parts` ×4 (`Bolt`, `Washer`, `Bracket`, `Assembly`
root) → `POST /document/parts/{id}/import-features` (`source_format: stl`)
with a small procedurally-generated binary-STL cylinder per leaf Part (24–96
segments) → `POST /document/parts/{root}/occurrences` ×4 real seed
Occurrences (client-supplied id, `resolved_part_id` pointing at another Part
already in the same session) → `POST /document/parts/{root}/component-patterns`
×2 (one 10×8 linear grid, one 24-around circular) → `GET /document/parts/{root}/assembly-mesh`.

## What this session did

Investigated whether the existing FastAPI/OCCT backend could support a
VR/XR companion app (Quest 2/3 standalone + PCVR) with a **non-Flutter**
headset client, reusing the backend as-is. Read through
`backend/app/document/*`, `backend/app/sketch/*`, `client/lib/assembly/*`,
`client/lib/viewport3d/*`, `client/lib/sketch/local_solver/*`,
`client/lib/storage/*`, and the relevant docs
(`project-brief.md`, `assembly-scope.md`, `lod-strategy/`). Full write-up:
**`docs/vr-recon-2026-09-24.md`**.

Five-line summary of that report's findings (see the report itself for the
detail/file references):

1. Every import/tessellate/export/solve endpoint is plain JSON-over-HTTPS
   with zero Flutter coupling — directly reusable by any HTTP client,
   headset included.
2. Per-part/per-assembly glTF is realistic and mostly additive: the
   `assembly-mesh` endpoint already computes deduplicated per-part geometry
   + per-instance world transforms (a scene graph in all but serialization);
   it needs a new glTF encoder (sibling to `mesh_export.py::encode_glb`),
   not new geometry work.
3. The single-file native format (`native_format.py`) is genuinely backend-
   owned and Flutter-independent; the **multi-file assembly composition
   protocol** (`Occurrence.external_ref` resolution) is, by deliberate
   design, entirely client-side today (`assembly_graph_composer.dart` +
   Flutter's SAF/iOS-bookmark/desktop storage plugins) and has no backend or
   format-level definition to lean on.
4. Biggest reimplementation risk for a non-Flutter client: the **client-side
   2D sketch solver** (`client/lib/sketch/local_solver/*`, a Dart/FFI port
   of the backend's own `py-slvs` solver, built for drag responsiveness) —
   worse implications for a 3D VR drag interaction than for 2D sketching.
   Assembly-graph composition/storage is the second-biggest. Feature-tree UI
   and mate-solve authoring are comparatively cheap to reimplement (thin UI
   over already-portable backend data/ids).
5. Multi-user shared assemblies are blocked by more than the stateless
   design's headline claim — session identity conflates "which device" with
   "which document," there's no persistence beyond client-held files, no
   concurrency/merge model, no per-user auth, and no real-time push channel.
   This is new backend infrastructure, not a VR-client workaround, and was
   explicitly out of scope in the original project brief.

## What's pending

- Nothing from this recon session is implemented yet — it's a design/
  feasibility report only. If a VR companion is greenlit, the natural next
  steps per `docs/vr-recon-2026-09-24.md` are (in rough dependency order):
  1. Decide the glTF scene-shape questions in §2 (per-part files vs. one
     scene per call; server-side vs. client-side hidden-instance filtering)
     before building the new encoder/endpoint.
  2. Decide the assembly-file storage model for a headset (§3) — there's no
     SAF/desktop-filesystem equivalent on a standalone Quest, so this is a
     real design question, not a straight port.
  3. Decide the drag-interaction latency strategy (§4 item 1) — local solve
     reimplementation vs. solve-on-release vs. accept round-trip latency —
     before committing to an interaction model.
  4. Multi-user shared assemblies (§5) is a separate, larger backend
     project (session/document separation, persistence, concurrency model,
     push channel) — treat as out of scope for a first single-user VR pass.

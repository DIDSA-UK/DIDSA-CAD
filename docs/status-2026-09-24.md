## What's working

**New endpoint: `GET /parts/{part_id}/assembly-mesh.glb`**
(`backend/app/document/router.py`, `get_assembly_mesh_glb` + its two new
helpers `_assembly_glb_part_mesh_data`/`_walk_assembly_glb_instances`, right
after `get_assembly_mesh`). Same auth/session handling as the existing
`GET /parts/{part_id}/assembly-mesh` (both sit on the same router, no
endpoint-specific auth code needed - the global `X-API-Key`/session
middleware already covers it). Walks the exact same Occurrence/
`ComponentPattern` tree `get_assembly_mesh`'s own `_walk` does - forked
into its own function rather than shared, following the precedent
`_walk_assembly_export_bodies` already set for the `export/assembly-*`
endpoints (the same "don't risk the existing, already-tested assembly-mesh
path" reasoning, see that function's own docstring).

- **One glTF mesh per unique `part_id`** (per distinct colour used - see
  below), reusing the same `compute_part_bodies`/`compute_part_bodies_coarse`
  + `tessellate_shape` geometry the JSON `assembly-mesh` path already
  computes, merged into one `MeshData` per Part via the existing
  `_merged_body_mesh_data` helper (now accepts an optional `mesh_quality`
  param instead of being hardcoded to `DEFAULT_MESH_QUALITY`, so this new
  endpoint's own `quality` query param actually reaches tessellation -
  every existing caller of that helper is unaffected, since the param
  defaults to the same constant it used unconditionally before).
- **One node per placed instance** (`AssemblyOccurrenceInstance`-equivalent),
  carrying a world-space `translation` + glTF `rotation` quaternion. The
  axis-angle -> quaternion conversion is NOT duplicated: `router.py` imports
  `assembly_solver._quaternion_from_axis_angle` directly (a private name,
  same precedent as `test_assembly_solver_dof_math.py` already reaching
  into `assembly_solver._ResolvedGeometry`/`_independent_dof`) and converts
  its `(qw, qx, qy, qz)` output to glTF's own `(x, y, z, w)` node-rotation
  order at the point where the node dict is built
  (`app.document.mesh_export.encode_assembly_glb` itself takes the
  already-converted quaternion, not axis-angle - see below for why).
- **Colour**: one glTF material per distinct non-`None` instance colour
  (`Occurrence.color`'s existing `"#RRGGBB"` string), `baseColorFactor`
  only (straight 0-255 -> 0-1 scaling, no sRGB-to-linear conversion, same
  "keep it simple" convention every other encoder in `mesh_export.py`
  already follows). An instance with no colour override gets no
  `material` key on its primitive at all (renderer default), rather than
  a synthetic "default" material.
- **Hidden instances omitted by default**; `?include_hidden=true` includes
  them - the one behavioural difference from the JSON `assembly-mesh`
  endpoint, which always reports every instance's own `hidden` flag and
  leaves filtering to the client. A Quest client that just wants the
  visible scene doesn't have to decode-then-discard.
- **`quality`/`tier` respected**, identical semantics to `GET /parts/{id}/mesh`
  (`tier="coarse"` swaps in `compute_part_bodies_coarse` + `coarse_eligible_
  feature_ids` the same way; `quality` maps through the existing
  `mesh_quality_from_slider`).
- **Unindexed accessors** (deliberate, not a shortcut left half-done): each
  Part's positions/normals accessors are the same flat, unwelded
  triangle-soup `MeshData` already uses everywhere else in this codebase
  (3 fresh vertices per triangle, no sharing) - matching `encode_glb`'s own
  existing convention exactly. Vertex-welding at encode time (task point 6)
  was evaluated and **not built this session**: welding a flat triangle
  soup into an indexed buffer is a real dedup pass (hash each
  `(position, normal)` pair, reuse an index when both match within
  tolerance) that interacts with this encoder's other new complexity
  (per-part accessor sharing across colour-variant mesh entries) in ways
  worth its own focused pass rather than folding in unreviewed - kept
  unindexed, per the task's own explicitly-allowed fallback ("if not
  [simple], keep unindexed and note it in the status doc"). This is the one
  concrete follow-up worth prioritizing if the real Quest client's own
  measured payload size needs it (see the recon session's own ~90-100 KB
  *estimate*, not yet confirmed against this endpoint's real output).

**New encoder: `app.document.mesh_export.encode_assembly_glb`** (+
`AssemblyGlbInstance` dataclass), right after `encode_glb` in the same
module. Deliberately kept free of any pydantic/OCCT/`assembly_solver`
dependency (mirrors that module's own "these encoders only ever touch
already-tessellated data" docstring, and its existing pure-Python
testability - `test_mesh_export.py` runs with no OCCT installed at all).
This is *why* the axis-angle -> quaternion conversion happens in
`router.py`, not inside the encoder: `assembly_solver.py` imports
`OCC.Core`/`py_slvs` at module level, and pulling that into `mesh_export.py`
would have broken its OCCT-free testability for anyone running just that
one test file in a lighter sandbox. The encoder takes the quaternion
pre-computed instead.

One real design decision worth flagging explicitly: a glTF mesh entry is
actually keyed by **`(part_id, colour)`**, not `part_id` alone - a node
can't carry its own material override in plain glTF (materials attach to
primitives), so a Part whose placed instances use more than one distinct
colour gets one JSON `mesh` entry per colour used, each referencing the
*same* shared position/normal accessors (no geometry duplicated in the
binary buffer, only a few extra bytes of JSON per extra colour variant).
"Mesh count equals unique parts" (this session's own test requirement,
and the task's own point 2) holds in the common/tested case where every
instance of a given Part shares one colour - documented in both the
encoder's own docstring and the test that exercises the multi-colour case
explicitly (`test_assembly_glb_mesh_count_equals_unique_parts_when_colour_
is_uniform_per_part`).

**Roadmap placeholder added** (`docs/roadmap.md`, new entry under "Other
open items"): shared network storage + server-side assembly composition,

## Known bugs / caveats

- None introduced this session as far as either full test suite shows -
  both ran clean, no regressions.
- The `_merged_body_mesh_data` signature change (added an optional
  `mesh_quality` param, default unchanged) is backward compatible by
  construction, but every existing call site was left unaudited for
  whether any of them *should* now also be passing a real `quality` value
  through instead of relying on the default - out of scope for this
  session (none of the existing `export/*` endpoints that call it take a
  `quality` query param in the first place, so there was nothing to wire
  up), flagging only so a future session doesn't assume this was
  independently reviewed for those call sites.
- Real caveat inherited from `_merged_body_mesh_data`'s own pre-existing
  behaviour (unchanged by this session): a Part whose geometry comes from
  an imported mesh (STL import, no parametric features) won't respond to
  the `quality` param at all - session 2's own recon measurement already
  hit and documented this for the JSON endpoint; it applies identically
  here, since this endpoint reuses the same tessellation path. Not a
  defect introduced or fixed this session.
